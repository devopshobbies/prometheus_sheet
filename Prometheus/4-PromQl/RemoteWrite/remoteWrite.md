پرومتئوس (Prometheus) برای پایش‌های روزمره عالی عمل می‌کند. داشبوردها به سرعت بارگذاری می‌شوند، آلرت‌ها به موقع ارسال می‌شوند و تیم شما برای بررسی‌های روتین و دیباگ کردن به این متریک‌ها متکی است.

اما بعد با یک محدودیت آشنا روبرو می‌شوید: نیاز به داده‌های چند ماه قبل دارید، اما اینستنس پرومتئوس شما فقط بازه زمانی کوتاهی را ذخیره می‌کند. یا شاید پرومتئوس را در کلاسترهای متعددی اجرا می‌کنید و جابجایی بین آن‌ها سرعت بررسی‌ها را پایین می‌آورد. شاید هم کسی درخواست مقایسه داده‌های بلندمدت را دارد و متوجه می‌شوید داده‌های قدیمی دیگر در دسترس نیستند.

قابلیت **Remote Write** با ارسال متریک‌ها به یک دیتابیس بلندمدت (هم‌زمان با جمع‌آوری آن‌ها)، این مشکل را حل می‌کند. هیچ تغییری در نحوه جمع‌آوری داده‌ها توسط پرومتئوس ایجاد نمی‌شود؛ شما فقط مقصدی را اضافه می‌کنید که این متریک‌ها می‌توانند برای مدت بسیار طولانی‌تری در آنجا زندگی کنند.

در این راهنما، نحوه راه‌اندازی Remote Write، تنظیم (Tune) آن برای ترافیک پروداکشن و مدیریت مشکلات رایج را بررسی خواهیم کرد. چه یک اینستنس پرومتئوس را مدیریت کنید و چه ناوگانی بزرگ از آن‌ها را، این راهنما به شما کمک می‌کند ستاپی پایدار و با مدیریت آسان بسازید.

💡
اگر در دنیای پرومتئوس و متریک‌ها تازه وارد هستید، پیشنهاد می‌کنم بلاگ ما را بخوانید: [Prometheus چیست؟](https://last9.io/blog/what-is-prometheus/)

## شروع سریع: راه‌اندازی در ۵ دقیقه

قبل از اینکه وارد جزئیات تیونینگ یا انتخاب‌های طراحی شویم، سریع‌ترین راه برای فعال‌سازی Remote Write را مرور می‌کنیم. این روش زمانی مفید است که نیاز دارید پرومتئوس بدون درگیر شدن با جزئیات دقیق، متریک‌ها را به یک ذخیره‌ساز بلندمدت ارسال کند.

این بلوک را به فایل `prometheus.yml` خود اضافه کنید:

```yaml
remote_write:
  - url: https://your-remote-storage/api/v1/write

    # نگهداری اطلاعات احراز هویت در فایل‌ها
    basic_auth:
      username: prometheus
      password_file: /etc/prometheus/secrets/password

    # تنظیمات صف که برای اکثر ستاپ‌های پروداکشن خوب کار می‌کند
    queue_config:
      capacity: 10000
      max_samples_per_send: 2000
      max_shards: 200
      batch_send_deadline: 5s

    # حذف متریک‌های کم‌ارزش
    write_relabel_configs:
      - source_labels: [__name__]
        regex: 'go_gc_.*'
        action: drop
```

آدرس `url` را با اندپوینت بک‌اند خود (Thanos، Cortex، Levitate، Mimir یا هر ذخیره‌ساز سازگار با OTLP/Prometheus) جایگزین کنید.

پس از ری‌استارت کردن پرومتئوس، بررسی کنید که آیا نمونه‌ها (Samples) ارسال می‌شوند یا خیر:

```bash
curl http://localhost:9090/metrics | grep prometheus_remote_storage_succeeded_samples_total
```

اگر این عدد در حال افزایش است، Remote Write فعال است.
حالا می‌توانیم بررسی کنیم که هر بخش از این تنظیمات دقیقاً چه کاری انجام می‌دهد و چگونه باید آن را برای ستاپ خود تنظیم کنید.

## نحوه کارکرد Remote Write

ریموت رایت (Remote Write) تغییری در نحوه اسکرپ (Scrape) یا ذخیره‌سازی محلی داده‌ها توسط پرومتئوس ایجاد نمی‌کند. بلکه یک مسیر دوم اضافه می‌کند که همان نمونه‌ها را به ذخیره‌ساز بلندمدت ارسال می‌کند. در پشت صحنه، پرومتئوس چند کار را به ترتیب انجام می‌دهد:

۱. تارگت‌های شما را مثل همیشه اسکرپ می‌کند.
۲. هر نمونه را در لاگ پیش‌نویس محلی (WAL) ذخیره می‌کند.
۳. ورودی‌های جدید را از WAL می‌خواند و آن‌ها را دسته‌بندی (Batch) می‌کند.
۴. آن دسته‌ها را از طریق HTTP به اندپوینت ریموت push می‌کند.

می‌توانید جریان کار را این‌طور تصور کنید:

```
برنامه‌های شما ← پرومتئوس ← ذخیره‌سازی محلی (~۱۵ روز)
                      ↓
                     WAL ← صف (Queue) ← HTTP POST ← ذخیره‌سازی ریموت (نگهداری طولانی)
```

**یک نکته مفید:** اگر اندپوینت ریموت از دسترس خارج شود، پرومتئوس بلافاصله نمونه‌ها را دور نمی‌ریزد. پرومتئوس به بافر کردن داده‌ها در WAL برای حدود دو ساعت ادامه می‌دهد. وقتی بک‌اند دوباره سالم شد، پرومتئوس صف انتظار را خالی کرده و هرچه ذخیره کرده بود را ارسال می‌کند. تنها قطعی‌های طولانی‌تر از پنجره بافر WAL، داده‌ها را در معرض خطر قرار می‌دهند.

داده‌های ارسالی به سیستم ریموت با Protocol Buffers کدگذاری و با Snappy فشرده می‌شوند. پرومتئوس خودش این جزئیات را مدیریت می‌کند؛ شما فقط باید بگویید داده‌ها کجا بروند.

## چرا Remote Write ضروری می‌شود؟

پرومتئوس برای متریک‌های کوتاه‌مدت عالی است، اما چندین موقعیت عملی وجود دارد که ذخیره‌سازی اکسترنال را مهم می‌کند.

**الزامات نگهداری طولانی‌مدت (Long-Term Retention)**
پرومتئوس داده‌های اخیر را نگه می‌دارد و برای بازه‌های کوتاه بهینه شده است. حتی با تنظیمات retention بالاتر، رشد حجم دیسک و کندی کوئری‌ها به سرعت خودشان را نشان می‌دهند. تیم‌هایی که داده‌های تاریخی را برای ممیزی، برنامه‌ریزی یا مقایسه فصلی نگه می‌دارند، معمولاً از ظرفیت نگهداری محلی فراتر می‌روند.

**دیپلوی‌های متعدد پرومتئوس**
محیط‌های بزرگ معمولاً چندین سرور پرومتئوس اجرا می‌کنند (یکی برای هر کلاستر، منطقه یا تیم). این منجر به داشبوردهای پراکنده، مجموعه‌داده‌های ایزوله و کوئری‌هایی می‌شود که نمی‌توانند بین اینستنس‌ها اجرا شوند. ارسال متریک‌ها از هر پرومتئوس به یک بک‌اند مشترک، یک مکان واحد برای کاوش داده‌ها در تمام کلاسترها فراهم می‌کند.

**متریک‌ها به عنوان یک دارایی قابل بازیابی**
پرومتئوس همه چیز را به صورت محلی روی دیسک ذخیره می‌کند. خرابی نود، از دست رفتن دیسک یا پاک شدن تصادفی، تمام متریک‌های ذخیره‌شده را از بین می‌برد. Remote Write یک کپی دوم و بادوام از تمام نمونه‌ها فراهم می‌کند تا داده‌ها فراتر از چرخه حیات هر اینستنس پرومتئوس باقی بمانند.

**محدودیت‌های مقیاس‌پذیری**
با افزایش تعداد سری‌های زمانی (Series) فعال، پرومتئوس نهایتاً تحت فشار قرار می‌گیرد: کوئری‌های کندتر، مصرف حافظه بالاتر و افزایش I/O دیسک. یک الگوی رایج این است که پرومتئوس فقط داده‌های اخیر را نگه دارد (جایی که جستجوی سریع مهم است) و نمونه‌های قدیمی‌تر را به بک‌اندی که برای مقیاس‌پذیری افقی ساخته شده، منتقل کند.

💡
لیست کامل تنظیمات remote write را می‌توانید [اینجا](https://prometheus.io/docs/prometheus/latest/configuration/configuration/#remote_write) پیدا کنید.

## انتظارات پس از فعال‌سازی Remote Write

فعال‌سازی Remote Write تغییرات قابل پیش‌بینی‌ای در مصرف منابع پرومتئوس و جریان داده ایجاد می‌کند. مهم‌ترین موارد عبارتند از:

**افزایش مصرف حافظه**
‏Remote Write داده‌های اضافی را در حافظه نگه می‌دارد:
*   متادیتای سری‌ها برای جستجوی لیبل‌ها.
*   صف‌هایی (Queues) که نمونه‌ها را قبل از ارسال نگه می‌دارند.

در اکثر ستاپ‌ها، مصرف حافظه حدود ۲۰ تا ۳۰ درصد افزایش می‌یابد. برای اینستنسی که معمولاً با ۲ گیگابایت اجرا می‌شود، مصرف اغلب به سمت ۲.۵ گیگابایت می‌رود.

**رفتار بافر WAL**
پرومتئوس حدود دو ساعت از سگمنت‌های WAL را نگه می‌دارد، بنابراین این تبدیل به پنجره بافر می‌شود.
*   قطعی‌های کوتاه بک‌اند توسط WAL پوشش داده می‌شوند.
*   به محض پاسخگویی مجدد بک‌اند، پرومتئوس داده‌های صف‌شده را ارسال می‌کند.
*   داده‌های قدیمی‌تر از پنجره نگهداری WAL قابل ارسال مجدد نیستند.

**افزایش ترافیک خروجی شبکه (Egress)**
دیپلوی‌های بزرگ (سرورهای متعدد پرومتئوس یا ستاپ‌های بین منطقه‌ای) شاهد تجمیع این ترافیک خواهند بود که ممکن است برای بودجه‌های ترافیک خروجی یا محدودیت‌های پهنای باند اهمیت داشته باشد.

💡
همچنین، راهنمای ما در مورد [بهینه‌سازی‌های Prometheus Remote Write](https://last9.ghost.io/optimizing-prometheus-remote-write-performance-guide/) را بررسی کنید!

## پیکربندی‌های رایج Remote Write

در زیر پیکربندی‌هایی که معمولاً در دیپلوی‌های واقعی استفاده می‌شوند، آمده است.

**ارسال متریک‌ها به یک ذخیره‌ساز واحد**
یک ستاپ مینیمال که تمام نمونه‌ها را به یک سیستم ریموت فوروارد می‌کند (مثال در بخش Quick Start آمده بود).

**فوروارد کردن متریک‌ها به بیش از یک مقصد**
پرومتئوس می‌تواند همان داده‌ها را به چندین اندپوینت ارسال کند.
*   ذخیره‌سازی اولیه به علاوه یک نسخه ثانویه.
*   ذخیره‌سازی گرم (Warm) به علاوه آرشیو.

```yaml
remote_write:
  - url: https://primary-storage/api/v1/write
    name: primary
    queue_config:
      capacity: 10000
      max_samples_per_send: 2000

  - url: https://backup-storage/api/v1/write
    name: backup
    queue_config:
      capacity: 5000
      max_samples_per_send: 1000
```

**اضافه کردن لیبل برای شناسایی منبع**
وقتی چندین سرور پرومتئوس به یک بک‌اند واحد ارسال می‌کنند، `external_labels` به شناسایی منبع هر نمونه کمک می‌کند.

```yaml
global:
  external_labels:
    cluster: production-us-east
    environment: production
    datacenter: us-east-1a
```

**فیلتر کردن متریک‌های ارسالی**
همه متریک‌ها نیاز به نگهداری طولانی‌مدت ندارند. `write_relabel_configs` نگه داشتن یا حذف داده‌های خاص را قبل از خروج از پرومتئوس آسان می‌کند.

```yaml
remote_write:
  - url: https://storage/api/v1/write
    write_relabel_configs:
      # Drop Go runtime and process-level metrics
      - source_labels: [__name__]
        regex: 'go_.*|process_.*'
        action: drop
```

## تیونینگ (Tuning) برای محیط شما

ریموت رایت از مجموعه‌ای از پارامترهای صف استفاده می‌کند. پیش‌فرض‌ها برای بسیاری از ستاپ‌ها کار می‌کنند، اما محیط‌های بزرگتر یا حساس‌تر معمولاً نیاز به تنظیم دارند.

### پارامترهای کلیدی

**capacity**
تعداد نمونه‌هایی که یک ورکر (Worker) می‌تواند هم‌زمان در حافظه نگه دارد. مقدار بالاتر فضای بیشتری در زمان کندی شبکه یا فشار بار (Backpressure) می‌دهد، اما رم بیشتری مصرف می‌کند.

**max_samples_per_send**
تعداد نمونه‌هایی که در یک درخواست HTTP بسته‌بندی می‌شوند. دسته‌های بزرگتر سربار شبکه را کاهش می‌دهند؛ دسته‌های کوچکتر داده‌ها را زودتر ارسال می‌کنند.

**max_shards**
حداکثر تعداد ورکرهایی که پرومتئوس اجازه دارد اجرا کند. ورکر‌های بیشتر، توان عملیاتی (Throughput) کلی را افزایش می‌دهند اما مصرف حافظه و کانکشن‌های موازی را هم بالا می‌برند.

**batch_send_deadline**
مدت زمانی که پرومتئوس قبل از ارسال یک دسته نیمه‌پر صبر می‌کند.

### مثال‌های پیکربندی بر اساس سناریوهای واقعی

**محیط‌های با توان عملیاتی بالا (High Throughput)**
طراحی شده برای ارسال حجم بالا بدون عقب افتادن.

```yaml
queue_config:
  capacity: 20000
  max_samples_per_send: 5000
  max_shards: 500
  min_shards: 100
  batch_send_deadline: 5s
```

**شبکه‌های ناپایدار یا کند**
تحمل بیشتر برای تاخیر و کاهش تعداد کانکشن‌های فعال.

```yaml
queue_config:
  capacity: 20000
  max_samples_per_send: 4000
  max_shards: 100
  min_shards: 20
  batch_send_deadline: 10s
```

**مانیتور کردن صف**
این متریک‌ها دید واضحی از رفتار Remote Write می‌دهند:
* ‏  `prometheus_remote_storage_samples_pending`: نشان‌دهنده بک‌لاگ (Backlog). افزایش مداوم یعنی سرعت ارسال کمتر از سرعت اسکرپ است.
* ‏  `prometheus_remote_storage_shards`: تعداد ورکرهای فعال.
* ‏  `prometheus_remote_storage_samples_dropped_total`: باید صفر بماند. دراپ شدن نشان‌دهنده فشار روی صف یا خطای ارسال است.

💡
همین حالا پرومتئوس Remote Write را مستقیماً از IDE خود با هوش مصنوعی و [Last9 MCP](https://last9.io/mcp/) بهینه کنید.

## عیب‌یابی مشکلات رایج (Troubleshooting)

### ۱. توقف ارسال متریک‌ها
اگر بک‌لاگ رشد کند و `samples_pending` بالا رود، ابتدا اتصال پایه را تست کنید:
```bash
curl -I https://your-endpoint/api/v1/write
```
اگر اندپوینت سالم است اما صف پر شده، افزایش `max_shards` می‌تواند کمک کند.

### ۲. افزایش مداوم مصرف حافظه
برخی ستاپ‌ها پس از فعال‌سازی Remote Write شاهد رشد مداوم حافظه هستند. اگر بافرهای صف مشکل‌ساز هستند، کاهش تعداد شاردها یا ظرفیت بافر کمک می‌کند. اگر علت سری‌های با کاردینالیتی بالا (High-Cardinality) است، حذف لیبل‌های بی‌رویه یا هیستوگرام‌های غیرضروری تفاوت چشمگیری ایجاد می‌کند.

### ۳. افزایش غیرمنتظره هزینه‌های شبکه
اگر کلاستر تعداد زیادی درخواست کوچک ارسال می‌کند، تغییر به دسته‌های (Batches) بزرگتر و ورکرهای کمتر، سربار را کاهش می‌دهد. همچنین حذف متریک‌هایی که نیاز به نگهداری بلندمدت ندارند از طریق `write_relabel_configs` بسیار موثر است.

## تفاوت Remote Write 2.0 چیست؟

نسخه ۲.۰ انکودینگ کارآمدتری را معرفی می‌کند که مصرف شبکه را حدود **۵۰ تا ۶۰ درصد** کاهش می‌دهد و از هیستوگرام‌های بومی (Native Histograms) پشتیبانی می‌کند. اگر بک‌اند شما از نسخه ۲.۰ پشتیبانی نکند، پرومتئوس به طور خودکار به نسخه قبلی برمی‌گردد.

برای فعال‌سازی، پرومتئوس را با این فلگ اجرا کنید:
```bash
prometheus --enable-feature=remote-write-2.0 --config.file=prometheus.yml
```

### حالت Agent Mode چیست؟
پرومتئوس حالتی به نام Agent Mode دارد که ذخیره‌سازی محلی و قابلیت کوئری را حذف می‌کند و فقط اسکرپ و Remote Write را نگه می‌دارد. این برای کالکتورهای سبک (Lightweight) عالی است.
```bash
prometheus --config.file=prometheus.yml --enable-feature=agent
```

## جمع‌بندی

وقتی Remote Write را روشن می‌کنید، پرومتئوس از یک ذخیره‌ساز متریک محلی به جزئی از یک پایپ‌لاین بزرگتر تلمتری تبدیل می‌شود. الگوهای تیونینگ در این راهنما به شما کمک می‌کنند تا با تنظیم تعداد شاردها، اندازه بچ‌ها و پنجره‌های نگهداری، پایداری سیستم را حفظ کنید.

اگر نمی‌خواهید خودتان یک لایه ذخیره‌سازی بلندمدت را مدیریت کنید یا پارامترهای صف را تنظیم کنید، **Last9** در اینجا به کمک شما می‌آید. سرویس **Levitate** ذخیره‌سازی مدیریت‌شده Last9 برای پرومتئوس است که مخصوص بارهای کاری Remote Write ساخته شده است.

## سوالات متداول (FAQs)

**۱. آیا Remote Write جایگزین ذخیره‌سازی پرومتئوس می‌شود؟**
خیر. پرومتئوس همچنان داده‌های اخیر را به صورت محلی نگه می‌دارد.

**۲. آیا پرومتئوس داده‌ها را در صورت قطعی بک‌اند دور می‌ریزد؟**
پرومتئوس حدود دو ساعت داده را در WAL نگه می‌دارد. اگر بک‌اند در این بازه برگردد، تمام نمونه‌ها ارسال می‌شوند.

**۳. چگونه بفهمم Remote Write عقب افتاده است؟**
متریک `prometheus_remote_storage_samples_pending` را بررسی کنید. افزایش آن نشانه لگ (Lag) در صف است.

**۴. چه چیزی هزینه‌های شبکه Remote Write را موثرتر کاهش می‌دهد؟**
حذف متریک‌های پرحجم ولی کم‌ارزش، حذف لیبل‌هایی که کاردینالیتی بالا ایجاد می‌کنند و افزایش سایز بچ‌ها.

**۵. آیا داشبوردها یا آلرت‌ها بعد از فعال‌سازی Remote Write نیاز به تغییر دارند؟**
خیر. داشبوردها همچنان پرومتئوس را به صورت محلی کوئری می‌کنند. Remote Write فقط روی داده‌های خروجی اثر می‌گذارد.
